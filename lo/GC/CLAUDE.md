# GC audit — conductor

## 1. Trigger

1.A. When Brian names a chapter ("GC17", "run GC13"), run the full chapter procedure in section 3. When he names a term family or corpus question, dispatch gc-term-grep instead. Anything else: ask.
1.B. When Brian says "check GCNN" (or says he has finished resolving), grep the chapter for [[ before dispatching anything. If markers are still standing, do not dispatch: tell him which numbers remain and stop, because a resolve-check run against unresolved markers burns a full agent to report what the grep already showed. When the chapter is clear, dispatch gc-resolve-check with the chapter number and the last marker number used in the chapter so far, so it can number its own findings onward from there, and relay its report verbatim. A PASS means the chapter is clean to commit.

## 2. Paths

2.B. English source:      lo/GC/00_source/GCNN_en.md

## 3. Chapter procedure

3.A. Preflight. Confirm 2.A and 2.B exist. If the chapter already contains [[ markers, stop and tell Brian — he resolves markers between runs. Check cleanliness with git status --short -- lo/GC, and read the result per 4.F: your chapter's file must be unmodified, and another chapter's file being modified is not your concern and never a reason to stop. Do not read the chapter body into your own context; grep only.
3.B. Size the chapter and split it. Batch size is measured in English words, never in paragraph or page counts: a printed page holds 348 to 380 English words but anywhere from one to eight paragraphs, so neither unit is a size proxy and a batch is never sized by counting them. Get the English word count with wc -w on the source file and the anchored paragraphs by grepping the "## {GC ###.#}" headings. Batch count is the English word count divided by 2200, rounded up; a chapter under 2700 English words runs as one batch. Cut at paragraph anchors, which may fall inside a page: walk the paragraphs in order accumulating their English word counts, and close each batch at the anchor whose running total sits nearest that batch's even share of the chapter. Balance is the point of cutting at paragraphs rather than pages, so never let a remainder pile onto the last batch — a final batch carrying double its siblings is the failure this rule exists to prevent. Ranges are stated as full anchors, from the batch's first anchor to its last, and consecutive batches must not share an anchor. State the split before the first dispatch and proceed; do not wait for approval.
3.C. Dispatch gc-batch-auditor per batch, SEQUENTIALLY, never in parallel (marker numbering and file appends depend on order). Each dispatch states: chapter NN, ref range, starting marker number, and whether it is the first batch (first batch creates the session files). Next batch's starting number = previous batch's reported last number + 1. A batch that wrote no markers reports a last number one below its starting number; the following batch then keeps that same starting number. The session files a batch writes are gcNN-companion.md and gcNN-glossary-proposals.txt and nothing else: never name gcNN-report.md to a batch, because a batch told the report is its to append will write batch narrative into a file gc-run-check later overwrites, and the narrative is lost. Where an earlier batch opened a lettered family under 6.C of the auditor's own file, name that family, its number and its last letter used, so the next batch continues the letters instead of opening a second number — and never tell a batch to leave a recurrence unmarked, which is what 6.C now forbids.
3.D. After the last batch, dispatch gc-run-check with three inputs: the chapter number, the expected total marker count, and the scoping paragraph required by 4.F. The expected total is the last marker number reported by the last batch that wrote any marker — not the sum of the per-batch counts. If no batch wrote a marker, skip the run-check and tell Brian the chapter came back clean.
3.E. If gc-run-check returned PASS and the proposals file has at least one section that is not "none", dispatch gc-glossary-merge with the chapter number and the fact that run-check passed. Never dispatch it on a failed run, and never during a run — it is the only agent allowed to write a governing file, and it may do so only once every batch has been judged against the frozen one. If run-check failed, skip the merge and say so.
3.F. Generate the resolution sheet before you report, with python3 lo/GC/04_assets/scripts/gc_resolution_sheet.py --chapter NN, and give Brian its path in your report. It writes one block per standing marker carrying that marker's anchor, note, proposed change and the full English paragraph, so he resolves without opening the source or the companion. It also reports damaged markers and unterminated brackets, which is how a stripped marker header gets caught before it reaches a check. Regenerate it whenever markers change or he says he has questions; it only reads, so running it again is always safe.

3.G. Report to Brian: the counts table from gcNN-report.md, any run-check failures, the merge report's applied and escalated counts, and any items the auditors raised for conversation. Nothing else. Brian resolves markers in Emacs and reviews the glossary changes with git diff; your run is done.

## 4. Rules

4.A. You orchestrate; agents work. Do not audit paragraphs or edit the chapter yourself.
4.B. Your context stays small: summaries from agents, grep output, the report. Never load full chapter or source texts.
4.C. Repo edits from a run are markers in the chapter file, nothing else. All other artifacts go to ~/claude-sandbox/gc-audit/.
4.D. Never transliterate Lao or Thai, and never let an agent summary that does so pass through to Brian.
4.E. Neither you nor a batch agent edits the governing files in 2.C. Proposed glossary rows and open-terms entries live in the proposals file. Only gc-glossary-merge writes to GC-glossary.txt and GC-open-terms.md, only after a passing run, and only the uncontested rows; GC-clergy-fixes.md is never written by any agent. Brian reviews every such change with git diff before committing. One exception, for repairs and not for decisions: where Brian has already adjudicated a point in conversation and applying it needs no judgment of yours — deleting a row he has declared stale, folding an exact duplicate into its developed twin, repairing a row whose pipe structure is broken without altering its content — make the edit yourself rather than spending an agent on it. Anything that requires choosing between two readings, or that writes a new row, still goes to gc-glossary-merge.
4.F. Concurrency. Brian audits several chapters at once in separate sessions, so cleanliness is scoped to your chapter, never to the tree. Another chapter's modified manuscript, and other chapters' rows in the 2.C governing files, are expected and never stop you — for writing as much as for checking: gc-glossary-merge writes into an uncommitted tree and refuses only the individual row another session has touched, escalating it for Brian. Never hold a merge back for a dirty tree, never ask him to commit another chapter's work to unblock yours, and never revert, stage, stash or commit it yourself. Before dispatching gc-run-check, run git status --short -- lo/GC and name in the dispatch which files belong to other chapters. run-check still fails your run if your chapter's diff holds anything but markers, if anything under lo/GC is untracked, or if a line added to a governing file cites one of your chapter's refs — that last means an agent of yours wrote where only gc-glossary-merge may. Before failing on an untracked path, run ls -l: a sandboxed session sees denied paths as character devices, and crw-rw-rw- owned by nobody is a sandbox artifact, not a defect. .claude directories and .mcp.json under lo/GC are that case every time — tooling scaffold, never repo content, never to be tracked, gitignored, or reported to Brian as work.

4.G. Reports are written for a reader who reads slowly and in four scripts. Every report you or an agent puts in front of Brian opens with a one-line verdict, then an action list of one line per item, each beginning with a status word in block capitals — FIX, BROKEN, DECIDE, OK, RESOLVED, WITHDRAWN, NOTE — followed by the marker number, the anchor, and one short clause saying what is wrong. NOTE is for something you changed or found that he should know about but need not act on; it goes in the list like every other item and is never left as loose prose for him to discover by reading. Then a line reading exactly "--- detail below, optional reading ---", and only below it any evidence or reasoning. Never put an action item below that line, and head every block below it with the same status word and label as the summary line it explains, so he can see what a paragraph is about before deciding to read it. Never report a clean check as prose: a pass that found nothing contributes one word to the OK line and nothing else, because a page explaining that the footnote chain is intact costs him time to discover he has nothing to do. That rule governs clean passes only and reverses when something is actually wrong — a broken footnote chain earns a FIX line at the top and as much detail below the line as the problem needs. Where a finding needs him to change something in a file, write it into that file as a [[FIX SEV #N|old -> new|note]] marker as well, so he jumps to it instead of hunting for it. Number the action items 1, 2, 3 so he can answer by number, and lead each line with what he must DO, before any explanation of why. Separate the items that need an action from the items that need none, and say plainly which is which, because a list that mixes them makes him read all of it to find the few that are his; put the sentence that divides them in bold, so the boundary is visible without reading. The detail below the line carries evidence he may want and nothing else: it never restates an action, and an item needing no evidence gets no block at all. A report whose action list cannot be acted on from the list alone has failed however accurate the prose beneath it, and length is itself a defect — he has said so of a report that was correct and unusable. NOTHING precedes the action list: not a preamble, not a verification note, not a sentence of context, not a finding you are pleased with. The first thing on the screen is what he must decide or do, numbered, with your recommendation named. Anything you want to tell him that is not an action goes below the list, and if that means a genuine discovery waits until the second half of the report, it waits — he has twice had to ask where the decision was, and both times the answer was sitting under something I put first.

4.H. When you edit an agent definition, a slash command, a settings file, or this file, write each numbered item as a single unwrapped line and let the editor wrap it on screen. Never hard-wrap prose in these files: a later reflow rewrites lines that did not change, and git diff stops showing what actually moved. Indented literal examples are the one exception and stay as indented blocks.

4.I. Context you load is the dominant cost of a run. Never read a manuscript or source file whole when an anchored range or a grep answers the question, never re-dispatch an agent to establish something a grep already settled, and pass an agent what you already know rather than letting it rediscover it. Corpus-wide evidence stays in scope; it is gathered with grep, which returns lines, not with reads, which return files.

4.J. Never use Lao or Thai digit characters — in a manuscript, a governing file, a marker, a report, or anything you put in front of Brian, numerals are always Western. The forbidden ranges are Unicode U+0ED0 to U+0ED9 for Lao and U+0E50 to U+0E59 for Thai; name them by codepoint rather than printing them, so that a sweep for stray digits does not flag the rule forbidding them. The rule exists because the substitution is invisible: the Lao digit zero closely resembles the vowel in ໂຣມ, so a form such as ຄຣິສຕະຈັກໂຣມ can silently become a variant that no grep will find again. Never let an agent's transcription of a Lao form reach Brian unverified — check it against the file with grep, because a term-sweep agent has already reported forms carrying a digit that existed nowhere in the manuscript, and only a grep separated the typo from a real defect.
