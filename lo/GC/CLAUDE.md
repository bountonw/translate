## 3. Chapter procedure

3.A. Preflight. Confirm 2.A and 2.B exist. If the chapter already contains [[ markers, stop and tell Brian — he resolves markers between runs. Check cleanliness with git status --short -- lo/GC, and read the result per 4.D: your chapter's file must be unmodified, and another chapter's file being modified is not your concern and never a reason to stop. Do not read the chapter body into your own context; grep only.
3.B. Size the chapter and split it. Batch size is measured in English words, never in paragraphs or pages: a printed page holds 348 to 380 English words but anywhere from one to eight paragraphs, so neither is a size proxy. Get the English word count with wc -w on the source file and the anchored paragraphs by grepping the "## {GC ###.#}" headings. Batch count is that word count divided by 2200, rounded up; a chapter under 2700 English words runs as one batch. Cut at paragraph anchors, which may fall inside a page: walk the paragraphs in order accumulating their English word counts and close each batch at the anchor whose running total sits nearest that batch's even share. Never let a remainder pile onto the last batch, which is the failure this rule exists to prevent. Ranges are stated as full anchors, first to last, and consecutive batches must not share an anchor. State the split before the first dispatch and proceed; do not wait for approval.
3.C. Dispatch gc-batch-auditor per batch, SEQUENTIALLY, never in parallel: marker numbering and file appends depend on order. Each dispatch states chapter NN, ref range, starting marker number, and whether it is the first batch, which creates the session files. The next batch's starting number is the previous batch's reported last number plus one; a batch that wrote no markers reports a last number one below its starting number, and the following batch keeps that same starting number. A batch writes gcNN-companion.md and gcNN-glossary-proposals.txt and nothing else: never name gcNN-report.md to a batch, because gc-run-check later overwrites that file and the batch narrative is lost. Where an earlier batch opened a lettered family under 6.C of the auditor's own file, name that family, its number and its last letter used, so the next batch continues the letters; never tell a batch to leave a recurrence unmarked.
3.D. After the last batch, dispatch gc-run-check with three inputs: the chapter number, the expected total marker count, and the scoping paragraph required by 4.D. The expected total is the last marker number reported by the last batch that wrote any marker — not the sum of the per-batch counts. If no batch wrote a marker, skip the run-check and tell Brian the chapter came back clean.
3.E. If gc-run-check returned PASS and the proposals file has at least one section that is not "none", dispatch gc-glossary-merge with the chapter number and the fact that run-check passed. Never dispatch it on a failed run, and never during a run — it is the only agent allowed to write a governing file, and it may do so only once every batch has been judged against the frozen one. If run-check failed, skip the merge and say so.
3.F. Run python3 lo/GC/04_assets/scripts/gc_resolution_sheet.py --chapter NN before you report and read its summary line: intact markers, damaged markers, unterminated brackets, and markers whose old side is not in the committed chapter. That last count means an agent typed a span from memory instead of copying it, so delete those markers and establish the finding again. The sheet the script writes is not a deliverable and Brian does not need its path; he resolves from your report and the marker notes. It only reads, so re-run it whenever markers change.

3.G. Report to Brian: the counts table from gcNN-report.md, any run-check failures, the merge report's applied and escalated counts, and those auditor items whose effects reach past their own site — outside the chapter, or several places inside it. Nothing else: a decision confined to one marker is settled at the cursor, and repeating it in the report makes him read the same thing twice. He resolves markers in Emacs and reviews the glossary changes with git diff; your run is done.

## 4. Rules

4.A. You orchestrate; agents work. Do not audit paragraphs or edit the chapter yourself.
4.B. A run's only repo edit is markers in the chapter file. Every other artifact goes to ~/claude-sandbox/gc-audit/.
4.C. Neither you nor a batch agent edits the governing files in 2.C; proposed rows and entries live in the proposals file. Only gc-glossary-merge writes to GC-glossary.txt and GC-open-terms.md, only after a passing run, and only the uncontested rows. GC-clergy-fixes.md is never written by any agent. Brian reviews every such change with git diff before committing. One exception, for repairs and not for decisions: where Brian has already adjudicated a point and applying it needs no judgment of yours — deleting a row he has declared stale, folding an exact duplicate into its developed twin, repairing broken pipe structure without altering content — make the edit yourself rather than spending an agent on it. Anything that chooses between two readings, or writes a new row, still goes to gc-glossary-merge. Any edit you make here obeys the 15-word limit in 4.H.
4.D. Concurrency, under root section 4. Cleanliness is scoped to your chapter, never to the tree. Another chapter's modified manuscript, and other chapters' rows in the 2.C governing files, are expected and never stop you — for writing as much as for checking: gc-glossary-merge writes into an uncommitted tree and refuses only the individual row another session has touched, escalating it for Brian. Never hold a merge back for a dirty tree. Before dispatching gc-run-check, run git status --short -- lo/GC and name in the dispatch which files belong to other chapters. run-check still fails your run if your chapter's diff holds anything but markers, if anything under lo/GC is untracked, or if a line added to a governing file cites one of your chapter's refs — that last means an agent of yours wrote where only gc-glossary-merge may. Before failing on an untracked path, run ls -l: a sandboxed session sees denied paths as character devices, and crw-rw-rw- owned by nobody is a sandbox artifact, not a defect. .claude directories and .mcp.json under lo/GC are that case every time — tooling scaffold, never repo content, never to be tracked, gitignored, or reported to Brian as work.

4.E. Report per the Reporting section of the repository CLAUDE.md, which is loaded in every session of yours but in none of your agents'; do not restate it here. Three things are specific to this audit. The reference mark on a summary line is the {GC ###.#} anchor, together with the marker number where the item has one. A FIX that needs Brian to change a manuscript is also written into that file as a [[FIX SEV #N|old -> new|note]] marker, so that he jumps straight to it instead of hunting for it. And two of the five agents write for Brian directly, so their reports are relayed verbatim — gc-resolve-check under 1.B and gc-term-grep under 1.A — because both return Lao spans, and reproducing Lao out of your own context rather than copying it is how a form comes back subtly wrong. The other three write for you, in numbered labelled items, and you compose Brian's report from them; never pass their prose through unchanged. Number every report item flat and consecutively — findings, notes and answers alike — and never renumber one, because Brian replies by number.

4.F. Context you load is the dominant cost of a run. Never read a manuscript or source file whole when an anchored range or a grep answers the question, never re-dispatch an agent to establish something a grep already settled, and pass an agent what you already know rather than letting it rediscover it. Corpus-wide evidence stays in scope; it is gathered with grep, which returns lines, not with reads, which return files.

4.G. Root 5.A and 5.C govern digits and transcription. One thing is added here: name a forbidden codepoint rather than printing it, so that a sweep for stray digits does not flag the rule forbidding them.

4.H. Governing-file entries are loaded by every agent on every dispatch, so length there is a tax the whole audit pays. A glossary row's Notes cell and a GC-open-terms.md entry each carry at most 15 words of prose, refs excluded, on one line: what an agent must DO — the approved form, the form that is wrong, and "mark any other form" where a family is closed. Counts, ref lists and reasoning are evidence rather than instruction. A run's evidence goes to that run's files in the sandbox; evidence you displace from a row you are shortening goes to the matching history file in 2.G, keyed by the English head. Enforce this on yourself and on any agent you dispatch.

4.I. Never apply a fix across chapters on your own initiative, however plainly a ruling of Brian's implies it: a decision about a rule is not permission to edit chapters outside the one under audit, and each corpus-wide fix needs his direction for that fix. What you owe him unprompted is the proposal with the evidence he decides from — how many sites, in which chapters, what changes at each, and which of those files another session has modified and therefore cannot be touched.

4.J. A brief that asks an agent to judge wording must say that the glossary guides and does not rule, and that the argument comes from the passage. An agent you dispatch knows only what the brief tells it.

## 5. Punctuation

5.A. Where English leaves a quotation open across the paragraphs of a multi-paragraph quote, Lao closes it. English opens such a quotation afresh at each paragraph and closes it only at the last, so its intermediate paragraphs carry no closing mark; the Lao translation closes every paragraph it opens. A Lao paragraph whose double quotation marks do not balance is therefore a defect even where the English at the same anchor leaves it open, and the English being open is never a reason to dismiss it. This is Brian's ruling, given on 14 August, and not a convention read off the corpus — a session that reads the corpus alone will infer the English rule and pass over real defects, which is what happened before he stated it.

5.B. Every sentence closes with a period, question mark or exclamation mark, and every footnote entry closes with punctuation, usually a period. A paragraph ending in a scripture citation carries the period after the closing bracket, and a footnote marker at that position follows the period, as (ພຣະນິມິດ 7:10, 12). and (ເບິ່ງ ໂຢບ 9:5 TKJV).[^26] — ruled by Brian on 14 August over nine sites that read the other way. A paragraph may end with a colon instead, but only where the next paragraph is the block quotation it introduces.

5.C. gc_punctcheck.py in 2.D enforces all of this and sixteen further classes, including the digits of 4.G and the invisible characters of root 5.B. Run it rather than checking by eye, and where you believe a finding is wrong, raise it with Brian rather than adding a case to the script: every exception the script learns is one it can no longer catch.

5.D. ແລະ takes a space on each side where it itemizes — two nouns, two verb phrases, the last member of a list — and closes up against the word after it where it opens a clause with its own subject and predicate. A joined ແລະ following a comma, semicolon, full stop or quotation mark is correct and is never raised. The rule is soft rather than mechanical, because a sentence carrying both uses reads as one flat list when the clause-opening instance is spaced like the itemizing one, so quote the whole sentence, say which job each instance is doing, and let Brian settle it rather than normalising either. This is Brian's ruling of 16 August, extended by him on 18 August.

## 6. QA3

6.A. Trigger. "qa3 GCNN" runs one chapter. "qa3 G1" runs a group from 6.B — and a group may be named GN, BN, batchN or groupN, with or without a space before the number, every form meaning group N: each chapter as its own agent chain, chapters in parallel because they are separate files, batches inside a chapter sequential because marker numbers and the record depend on order. "check GCNN" after QA3 resolution is the resolve-check of 1.B unchanged, with the classes named in 6.D passed to it. The translator's whole calling sequence for the pass is eight commands — qa3 GC12 for the pilot, then qa3 G1 through qa3 G6 — plus a check GCNN per resolved chapter; the batches inside a chapter are dispatched by the conductor and never appear in a trigger.
6.B. Groups, sized by the English words behind the changed paragraphs: G1 GC01–05, G2 GC06–08, G3 GC09–13, G4 GC14–19, G5 GC20–30, G6 GC31–42. GC12 runs alone first as the pilot that sets the marker threshold, so G3 runs without it.
6.C. Scope is the text QA1 and QA2 changed: every paragraph whose Lao differs between the pre-QA baseline at 8802e1bb and the working tree — the text prepared for printing; the book has not yet been printed. Nothing else is read. Preflight as in 3.A, then build the packet with python3 lo/GC/04_assets/scripts/gc_qa3_packet.py --chapter NN, which writes ~/claude-sandbox/gc-audit/gcNN-qa3-packet.md and prints the batch split. State the split, then dispatch gc-qa3-reader per batch with the chapter, the packet path, the anchor range, the starting marker number, the record path of 6.E, whether it is the first batch, and any carried-over sites of 6.G that fall in the range. Markers restart at #1 in every chapter.
6.D. The reader judges every change inside its whole paragraph; the glossary guides and never rules, and its brief already says so. It writes markers of class REVERT, REWORD or FIX at HIGH or MED only; there is no LOW. Term sites carry ranked candidates in the marker note. No proposals file is written and gc-glossary-merge is never dispatched: the governing files are untouched by QA3, and its record is the evidence for their later rework, which is entry 17 of lo/GC/04_assets/planning/SIDEQUESTS.md. A true finding that is glossary business — a row that should change, a row that is missing, a family that wants narrowing — is not decided in this pass: the conductor appends it as one line under entry 17, where the rework reads it, which is the translator's ruling of 25 August.
6.E. The record lives at lo/GC/04_assets/qa3/GCNN.md, one file per chapter, committed with the chapter. It is the evidence that every change was re-read in context, and the translator will be asked for it.
6.F. After the last batch of a chapter, run python3 lo/GC/04_assets/scripts/gc_resolution_sheet.py --chapter NN and read its summary line as in 3.F; a marker whose old side is not in the chapter is deleted and established again. Then dispatch gc-run-check with the chapter number, the expected marker total and the scoping paragraph of 4.D, telling it that the classes are REVERT, REWORD and FIX and that no companion or proposals file exists. The group report gives, per chapter, the marker count by class, the runs judged and the STANDS count, then only those reader items whose effects reach past their own site, in the report shape of the repository CLAUDE.md; a verdict confined to one marker is settled at the cursor and is not repeated.
6.G. Two carried-over questions are in scope though their text did not all change, because the translator has agreed to settle them in this pass: the Vicar of Christ family of SIDEQUESTS entry 1 — GC03 {GC 50.2}, {GC 51.3}, {GC 53.2}, {GC 55.1}, {GC 59.1}; GC04 {GC 62.4}; GC05 {GC 92.2}; GC06 {GC 101.1}, {GC 102.1}; GC33 {GC 567.3}; GC35 {GC 591.1} — and the justification-by-faith sites of entry 14 — GC14, the subheading above {GC 253.2}, {GC 253.2} and {GC 256.3}. Name them in the dispatch of the batch that holds them. For the Vicar sites the Thai GC is the comparison: both Thai editions are on origin/main under th/GC/04_assets/editions/print/ and alt/, and checked out at /home/ton/programming/translate-th-GC; read the matching paragraph there or with git show origin/main:PATH, never by merging. Both Thai editions are poor translations kept for reference, on the translator's ruling of 25 August: what they did is reported as a data point, weighed with extreme caution, and adopted only where it is a real improvement on its own merits. Both entries leave the queue when their sites are resolved.
6.H. Dictionary coverage, twice per chapter. Run python3 lo/GC/04_assets/scripts/gc_dictcheck.py --chapter NN when you build the packet, and again at check GCNN once the translator has resolved. It loads the same dictionary hierarchy the typesetting pipeline loads — chapter and book dictionaries and patches, then patch.txt and main.txt under lo/assets/dictionaries/ — and reports every changed token those dictionaries cannot segment, with the stretch they cannot bridge and the token's count in the pre-QA book. Name each flagged token in the dispatch of the reader batch that owns its anchor on the first run, and in the gc-resolve-check dispatch on the second: a typo takes a FIX marker, and a genuine new word comes back with a proposed coded row. After the chapter passes, append the confirmed rows to lo/assets/dictionaries/main.txt under a comment line naming the chapter, and tell the translator to review them with git diff before committing. Rows are appended, never edited into existing lines, so another session's uncommitted dictionary work is never touched.
